Chapter 9

Forms and Actions

The humbling case for plain elicitation, validation for two users, consent without nagging, and undo when the model pressed the button.

This is the chapter with the most code in it, because forms are where most MCP Apps end up, and because forms are where the two-user problem stops being philosophy and starts being a bug report. We start with the case that should worry you.

The humbling case

Core MCP can already ask the user a structured question without any app at all. The server sends an elicitation as part of a tool call; in revision 2026-07-28 this rides on the multi round-trip request mechanism, which exists precisely so the server does not need a socket or a sticky session while it waits for an answer. The host renders the question in its own components, with its own styling, accessibility, keyboard handling, and consent flow. You provide a schema, and you get an answer back.

That path is free, works in every host that speaks core MCP, is consistent with every other prompt the user has seen in that client, and inherits accessibility work you did not do. Your custom form has to be better than that. Sometimes it is. Often it is not, and the honest test takes about a minute.

Elicitation wins when the question is short, the fields are independent, the values are simple, and there is nothing to show the user while they answer. Three text fields and a dropdown is an elicitation; stop building. Your app wins when at least one of four things is true: seeing the data matters, because the user is choosing among things they need to look at; the fields interact, so changing one changes what the others should say and showing that live is the whole point; there is a preview, and the user needs to see the consequence before committing; or direct manipulation is faster than typing, because dragging a bar beats typing four numbers that have to add up.

Notice what is not on that list. Branding is not on it. Familiarity with your product is not on it. The fact that you already have the components is emphatically not on it. Those are reasons your team wants an app, and they are not reasons your user needs one. Run this test honestly once and you will delete something, and that is the chapter doing its job before you have read the rest of it.

Validation for two users

Assume you passed the test and you are building the form. Now you have two users who both need to be stopped from doing the wrong thing, and they need to be stopped in different languages.

The model is stopped by the schema: types, enum, required, exclusiveMinimum, format. These are read before the call, so a well-declared schema prevents the bad call rather than rejecting it afterwards. The human is stopped by a message, in place, next to the field, in words, saying what the rule is and how to satisfy it. And both must be enforced by the server, because the app is a client and clients lie, usually not out of malice but out of being an older version that somebody’s host cached.

The failure mode is having those three in three places, written by three people, disagreeing. So: one rule, three renderings, derived from one statement of it. Here is the gallery’s version, where the rule is that expenses over $500 need a justification. In the schema, justification is a string with a description saying when it is required. In the server handler, where it is actually enforced:

run(args) {
  if (args.amount > 500 && !args.justification) {
    throw new Error("Expenses over $500 require a justification.");
  }
  // ...
}

And in the app, where it is explained:

function validate() {
  if (!(draft.amount > 0)) return "Amount must be greater than zero.";
  if (draft.amount > 500 && !document.getElementById("just").value.trim()) {
    return "Expenses over $500 need a justification.";
  }
  return "";
}

Three appearances, one sentence, one threshold. If the threshold changes, three lines change, and a test catches you if you miss one.

Two things in that figure are worth stealing. The message names the rule and the threshold, and it sits next to the control that fixes it, which you should compare against a red border, telling the user something is wrong and nothing else, or a toast, telling them something is wrong and then leaving. And the label changed before the error appeared: at $62 the field reads Business justification with the placeholder One line, optional, while at $842 it reads Business justification (required over $500). A field labelled optional that then refuses to submit has told the human one thing and the server another, which is a small betrayal that people remember longer than you would expect.

Errors that the model can use

There is one more audience for your error messages, and it is the one that will actually retry. When a tool call fails, the model reads the failure and then decides whether to try again, try differently, or tell the user, and what it decides is determined entirely by what your message says.

Compare Error: validation failed against Expenses over $500 require a justification. Call submit_expense again with a justification string describing the business purpose. The first produces an apology to the user; the second produces a fixed call. Writing the second one costs nothing and turns a dead end into a recovery.

Two mechanical notes. Tool failures belong in the result with isError: true rather than as JSON-RPC protocol errors, because the model is supposed to read them and protocol errors are for the transport. And say what to do next rather than only what went wrong: an error message here is an instruction to the second user, not a verdict on the first one.

Destructive actions in a consent medium

Now the sharp end. Your app can call tools, some of those tools delete things, and the button that triggers them can be pressed by a human who read the screen or by a model that inferred intent from a sentence.

The instinct is to add a confirmation dialog, and the instinct is half right. The question is what the confirmation is for. A confirmation that says “Are you sure?” is not a safety mechanism; it is a speed bump the user learns to jump in about four repetitions, and after that it is worse than nothing, because it creates a sense of protection that no longer exists. A confirmation is only worth showing if it tells the user something they did not already know, which means it names the specific thing and the specific consequence. “Delete orders-2026-prod? 4.2M rows. This cannot be undone.” is worth reading, and people do. “Are you sure you want to delete this item?” trains people not to read the first one.

Three rules follow. Name the object and the scale, because “this item” is not a name and “4.2M rows” is a scale. Say whether it is reversible, honestly, since “this cannot be undone” is information and, if it can be undone, saying that instead and dropping the alarm is better than crying wolf on the one occasion it matters. And do not put a destructive action next to a frequent one: Krug’s version of that rule was about misclicks, and here it is worse, because the model might call the tool directly, proximity in your UI often becomes proximity in your naming, and confusable names are a real source of wrong tool calls.

The confirmation, written out

Copy is design here, so here is the copy for a confirmation that has to earn a read.

Void expense EXP-40122?

$842.00 to United Airlines, filed 14 August, already approved by Dana Okafor. Voiding notifies Dana and removes it from the August close.

[ Void it ] [ Keep it ]

Four things it does that “Are you sure?” does not. It names the object with enough detail to recognise the wrong one, so if the model picked the flight when the user meant the coffee, that is visible in the first line. It states the blast radius, because somebody else finds out and something else changes, and those are the facts that turn a reflex into a decision. Its buttons say what they do rather than OK and Cancel, so a user who reads only the buttons still gets it right, and a lot of users read only the buttons. And it does not shout: no red banner, no warning triangle, because the information is the warning and decoration on top of information reads as decoration, which people learn to skip.

Where the confirmation lives matters too. Inside the widget, when the widget is already on screen and the action came from a button in it. In its own render, when the action came from the conversation, because the model called void_expense, the host is about to run it, and a card that summarises it before it happens is the whole interface. The second case is the one people forget to build, and it is exactly the case where the model rather than the human chose the object.

Undo, when the model pressed the button

This is the requirement the second user creates, and most teams have not thought about it. On the web, the person who clicked the button read the button. Here they may not have: the model called submit_expense because the user said “yeah, file it”, and the model’s interpretation of “it” was an inference. Inferences are usually right, and usually is not a safety property.

So for every tool that changes something, ship the tool that changes it back. That is not a preference. It is a design requirement created by the fact that one of your users is a probabilistic system acting on a human’s behalf. The gallery does this: submit_expense has a sibling called void_expense whose description says when to reach for it, and the successful result tells both users it exists.

app.setContext(
  "Expense EXP-40122 submitted: $62.40 at Blue Bottle Coffee on 2026-08-14. " +
  "Reversible with void_expense.",
  { expenseId: "EXP-40122", amount: 62.4, undoTool: "void_expense" }
);

The human sees Ask me to void it if that was wrong. The model sees the tool name. When the user says “no, wait, that was the personal card”, the recovery is one turn and no apology. Where something genuinely cannot be undone the design changes shape, because then the confirmation is the only line of defence and it has to earn its place: name the object, state the scale, say plainly that it is permanent, and put the burden on the click rather than on a checkbox nobody reads.

Latency, and the button that lies

Actions in this medium are slow in a way web forms are not. A click becomes a postMessage, a host decision, possibly a consent prompt, a network call, and a response. Half a second is optimistic and two seconds happens, which makes the pressed state a design surface rather than a detail.

Disable on press, immediately, because double submission is a real failure here and the round trip is long enough for a person to press twice. Say what is happening in the button itself, since Submitting… beats a spinner beside it when the user is already looking at the button. Keep the form readable while it is in flight, so do not blank the fields or overlay the card, because if it fails the user needs to see what they were submitting. And handle the consent prompt case, where the host puts a dialog in front of the user and your app finds out nothing until they answer: your pressed state might sit there for ten seconds while somebody reads a permission dialog, and it should still look sane at second nine, which rules out anything that animates impatiently.

On failure, restore the state and say what happened in place. A toast that appears and leaves is worse than useless here, because the widget it was describing is still on screen looking unchanged.

Four failures, one form

Everything above, applied to the same widget. These are the four things to look for in review, in the order they bite.

Fields the model could have filled is the first, which is Chapter 4’s law: count the fields, count the genuinely unknown values, and if those numbers differ, fix the schema rather than the layout. Validation the human sees and the model does not is the second, where inline messages sit on top of an empty schema, so the model calls with values your UI would have rejected, the server throws, and the user watches the assistant fail at something they were about to do correctly. Submission the model never hears about is the third: the form posts, the widget shows a tick, and nothing is written back, so three turns later “did that go through?” and nobody knows, when one setContext call at the moment of success with the identifier in it would have closed it. And an action with no way back is the fourth, where the review question is not “is there a confirmation” but “what does the user say to undo it, and does that work”.

Fix all four and the form in Figure 4-2 is what you get: four assumptions shown, one question asked, one rule stated before it is enforced, one result written back, and one sentence telling both users how to reverse it.

What to remember

Check whether a plain elicitation beats your form, and accept the answer. Write the rule once and render it three ways: schema for the model, message for the human, enforcement on the server. Make error messages instructions rather than verdicts. Confirm only when the confirmation carries information the user did not have. And ship the undo, because one of your users pressed the button on an inference.
