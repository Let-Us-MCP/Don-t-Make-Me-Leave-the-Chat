Chapter 2

Your App Has Two Users

The book's thesis: the human reads pixels, the model reads schemas, and both can be failed.

Law 2

Your app has two users. One of them reads pixels. The other reads schemas.

This is the idea the rest of the book is built on, so here it is stated plainly before we do anything with it.

When your widget renders, two entities are looking at it. The human sees a card, three rows, and a blue button. The model sees your tool’s name, your tool’s description, the JSON Schema of your inputs, and whatever structuredContent you handed back. Those are different perceptual systems reading different artefacts, and neither of them can see the other’s.

Every usability book ever written assumed one user. This one does not, and that assumption is the reason a lot of otherwise beautiful MCP Apps do not work.

Affordances, for something with no hands

Don Norman gave us the vocabulary. An affordance is a property of a thing that tells you what you can do with it. A handle affords pulling. A flat plate affords pushing. Doors get this wrong constantly, which is why he ended up famous for them.

The model has affordances too. They are just not shaped like handles.

For the model, the affordances of your app are:

  • The tool name. compare_rates affords comparing rates. loan_analytics_suite_v3 affords nothing; it names a product, not an action.
  • The tool description. This is the door handle. It is the single most important string in your entire application, and it is usually written last, by whoever was still in the office.
  • The input schema. Types, enums, required fields, defaults, and the per-property descriptions that almost nobody writes. Every constraint you declare is a constraint the model does not have to guess.
  • The returned content. What the model gets to keep after your pixels are gone.

Look at the description on the gallery’s fixed rate comparison tool:

Show a comparison of the loan offers under discussion, ranked by total
cost over a horizon the user can adjust. Use when the user asks which
loan is cheapest, or wants to see how the answer changes if they pay
it off early.

Two sentences. The first says what it does. The second says when to reach for it, in the words a user would actually use. That second sentence is the door handle. Without it the model has to infer applicability from a name, which is how you end up with a beautiful app that never gets invoked, and a developer who concludes that hosts are broken.

Now the before version:

Open the loan analytics suite to compare offers, view amortization
schedules, run sensitivity analysis, and export results.

Four capabilities, no trigger conditions, and the verb is “open”. The model reads that and learns that this tool opens something. Opening things is not a user goal. Nobody has ever wanted to open a suite.

The description formula

Descriptions are the highest-value strings you will write, and most people freeze in front of them. Three sentences, in this order, and you can stop:

  1. What it does, in the user’s vocabulary, not your product’s.
  2. When to use it, phrased the way somebody would ask.
  3. When not to, if there is a near neighbour it could be confused with.

Applied to the gallery’s clause finder:

Show the clauses in the contract that govern a topic, quoted, with the governing words highlighted. Use when the user asks what the contract says about something.

Two sentences, because there is no near neighbour. Applied to the flight picker, which does have one:

Show the shortlisted flights for a route and date already established in the conversation so the user can pick one. Use when the user has said where and when they are going and now needs to choose. Do not call this before origin, destination, and date are known.

That third sentence is a real constraint, and a model will honour it. Negative space is part of the door handle, and it is the part nobody writes.

One more habit worth forming: write the description before you build the widget. If you cannot say when somebody would want this in one sentence, the widget is not going to fix that.

Feedback, for something that was not watching

Norman’s other big idea was feedback: after you act, the system tells you what happened. Press the button, hear the click.

In this medium there is a second feedback channel, and it is the one people forget. When the human interacts with your widget, the model does not automatically find out. The iframe is sandboxed. The host cannot read into it, which is the entire point of the sandbox. Unless you say something, everything that happens inside your app happens in a room the other user is locked out of.

So say something. That is what ui/set-context is for:

app.setContext(
  "Comparing over 5 years: Cedar Credit Union is cheapest at $34,835 total.",
  { horizonYears: 5, cheapest: "Cedar Credit Union", totalCost: 34835 }
);

Two arguments, because there are two users. The string is for the model to read and quote. The object is for anything downstream that wants to compute rather than parse.

The rule of thumb: any state change a user would mention out loud, mention to the model. If the human would say “okay, I moved it to four years”, write that back. If they moved the mouse, do not.

Do not write back on every keystroke either. The context window is a shared budget and you are spending somebody else’s. One line per meaningful state change, phrased as a sentence a person would say. High-Performance MCP Applications has a whole chapter on what that budget costs; for our purposes, the design rule is enough.

Teardown: two budget allocators

The task: “help me split next quarter’s $120k.”

This one is genuinely nicer to use than it looks. Freehand drawing, undo, snapping. Somebody cared.

Look at the right-hand column. That is the transcript view of what the model knows after the user spends four minutes in there, and it is empty. Not summarised, not lossy. Empty.

Here is how that plays out. The user drags for a while, closes the widget, and types: “okay, draft the email to finance with those numbers.”

The model has no numbers. It will do one of three things, all bad. It will ask the user to repeat what they just spent four minutes expressing, which makes the widget a waste of time. It will call the tool again and get the default allocation, which makes the email wrong in a way nobody catches. Or it will guess, which makes the email wrong in a way nobody catches and sounds confident.

The failure is not that the canvas is ugly. It is that the canvas is opaque, and opacity is a bug when one of your users can only see through the API.

Same interaction. Drag a bar, money moves. The difference is eleven lines at the end of the drag handler:

function up() {
  app.setContext(
    "Budget now: " + items.map(it => it.name + " " + money(it.amount)).join(", ") + ".",
    { cap: cap, allocation: items }
  );
}

Now “draft the email with those numbers” works, because the numbers are in the conversation. The user never sees this code run. What they see is that the assistant seems to know what they just did, and they will describe that to a colleague as the app being smart.

It is not smart. It is legible. Legible is achievable on a deadline.

What a write-back costs

Context is not free and it is not yours. Every string you write back is tokens in somebody’s window, on every subsequent turn, forever.

Which gives you a budget and a shape:

  • One line per meaningful state change. Not per keystroke, not per hover.
  • Prefer replacing over appending. The current state is worth more than its history. “Comparing over 4 years” replaces “Comparing over 5 years”; you do not need both.
  • Put the detail in structuredContent, the meaning in the text. The text is what gets read on every turn. The object is what gets used when somebody acts.
  • Numbers, names, and identifiers earn their place. Adjectives do not. “The user selected a flight” is a wasted line. “User picked UA 512 departing 07:15 for $318” is an answer to the next three questions.

The failure mode at the other extreme is real too. An app that writes nothing back is cheap and useless. Aim for the smallest sentence that would let a colleague pick up the task from a cold start.

One source, two renderings

Here is the mechanical version of Law 2, and it is the part that keeps you out of trouble at three in the morning.

A tool result carries content for the model and structuredContent for your app. The temptation is to compute them separately, because they have different shapes. The consequence is that they drift, and when they drift, your two users are told different things about the same fact, and the human is the one who finds out.

The gallery avoids this by computing once. priceOffers() in gallery/fixtures.js prices every horizon from one to ten years, the handler puts that table in structuredContent, and the app does no arithmetic at all. It reads offer.totals[years]. When the slider moves, the number on screen and the number in the model’s context come from the same line of code, because there is only one line of code.

If your widget computes something the server did not, you now have two implementations of one truth. That is a bug with a countdown timer on it.

What the model actually sees

Abstractions are easy to nod at. Here is the literal artefact, for the gallery’s fixed rate comparison, as it appears in the model’s context.

{
  "name": "compare_rates",
  "title": "Compare loan rates",
  "description": "Show a comparison of the loan offers under discussion, ranked by total cost over a horizon the user can adjust. Use when the user asks which loan is cheapest, or wants to see how the answer changes if they pay it off early.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "horizonYears": {
        "type": "integer", "minimum": 1, "maximum": 10, "default": 5,
        "description": "Starting comparison horizon. The user can change it in the app."
      }
    }
  },
  "_meta": { "ui": { "resourceUri": "ui://rate-compare/after" } }
}

That is the whole interface. No pixels, no layout, no colour. A name, a paragraph, a schema with one property, and a pointer to something the model cannot look at.

Read it as a user would. What does it tell you?

That there is a thing called comparing rates. That it ranks by total cost. That there is a horizon, that it is a whole number of years between one and ten, that five is normal, and that the human can change it after the render. That last clause is doing real work: it tells the model not to re-call the tool when the user says “what about four years”, because the widget can handle it.

Now the same view of the before version:

{
  "name": "compare_rates_suite",
  "title": "Loan analytics suite",
  "description": "Open the loan analytics suite to compare offers, view amortization schedules, run sensitivity analysis, and export results.",
  "inputSchema": { "type": "object", "properties": {} },
  "_meta": { "ui": { "resourceUri": "ui://rate-compare/before" } }
}

An empty schema. There is exactly one thing this tool can be asked for, so “compare those at three years” cannot be expressed. The user will type it, the model will call the tool anyway, and the widget will render its default view, and the user will conclude that the assistant did not listen.

The pixels were never the problem.

The design review question

Adopt one habit from this chapter and make it this one. In every design review, for every screen, ask:

What does the model see when this renders?

Not “what does the API return”. What does the model see: the name, the description, the schema, the content string, and whatever comes back over ui/set-context while the human is working.

The question is disruptive in a useful way, because in most reviews nobody can answer it. The design file has pixels. The schema is in a different repository, written by a different person, six weeks ago. That gap is where these applications fail, and the question is a flashlight you can point at it in thirty seconds.

The gallery’s mini host puts a “what the model sees” pane next to every render for exactly this reason. It is the panel visible in Figures 2-1 and 2-2, and it is the most useful thing in the whole development loop. Build one. It costs an afternoon and it changes what your team argues about.

The failure that looks like a model problem

One pattern worth naming, because it gets misdiagnosed constantly.

A team ships an app. It works in demos. In use, the assistant “keeps getting confused”, “forgets what the user did”, or “asks things it should know”. The conclusion in the retro is that the model is not smart enough yet.

Almost always, it is one of three things from this chapter.

The description never said when. The model calls the tool sometimes and not others, which reads as inconsistency. It is not inconsistent; it is guessing, because you gave it a definition rather than a trigger.

The app never wrote back. The user did something, the model did not find out, and the next answer ignores it. The user experiences this as the assistant not paying attention, which is exactly what happened, and exactly whose fault it is.

The two channels disagreed. The widget computed one number and the text carried another. The model quotes the text, the user is looking at the pixels, and one of them is wrong.

None of those is a model capability problem, and all three are fixed by editing strings and adding one function call. When somebody on your team says the model is confused, the first question is Law 2’s question: what does the model see when this renders?

What to remember

Your app has two users. The human reads pixels and forgives a lot. The model reads names, descriptions, schemas, and text, and forgives nothing, because it cannot see what it was not told.

Write the description as though it were the only thing you shipped, because for one of your users it very nearly is. Write state back when a person would have said it out loud. Compute the fact once and render it twice.
