Chapter 4

Never Ask What the Conversation Already Knows

Prefill from context, make it correctable, and treat every click as a tax.

Law 3

Never ask what the conversation already knows.

This is the law with the shortest path from violation to insult. The user typed the answer. It is above your widget on the screen, in their own words, in their own message, thirty seconds ago. Your app rendered an empty field asking for it, and the user is now retyping something they already said, into a box, inside a conversation whose entire premise is that they should not have to do that.

Krug’s version of this law is about mindless choices: the interface asks a question the user has no basis to answer or no interest in answering, and every one of those is a small tax on getting anything done. Our version is worse, because the answer was not merely obvious from context. It was stated, out loud, by the person now being asked for it.

What the conversation knows

More than you think, and it accumulates. By the time your tool is called the model is sitting on what the user said explicitly in this session; what they said three turns back, which they will absolutely expect you to remember because a person would have; what previous tools returned, including yours if you have been called before; and what the model has already inferred, which is why “my usual cost centre” resolves to CC-ENG-7 when a lookup two turns ago produced that string.

All of it is available to you, and the mechanism is completely unglamorous: put the fields in your input schema, describe them, and the model fills them in when it calls you. That last clause is the part people miss. A field the model can fill is a field the user never sees. Your input schema is not a validation artefact bolted on at the end. It is the list of questions you are choosing not to ask, and writing it is a design activity that happens to produce JSON.

Compare the two expense tools in the gallery. The before version declares inputSchema: { type: "object", properties: {} }. No inputs, so the model passes nothing, so the app knows nothing, so the app asks for everything: nine fields, in a chat, for a $62 coffee. That empty object is not a neutral default. It is the decision to interrogate the user, made accidentally, in a file nobody reviewed.

The after version declares five properties:

inputSchema: {
  type: "object",
  properties: {
    merchant: { type: "string", description: "Who was paid." },
    amount:   { type: "number", exclusiveMinimum: 0, description: "Total charged." },
    currency: { type: "string", default: "USD" },
    date:     { type: "string", format: "date", description: "Date of the purchase." },
    category: { type: "string", enum: ["Travel", "Meals", "Software", "Other"] },
  },
}

The model fills all five from one sentence of user input, and each declaration is doing a specific job. The enum on category means the model picks from a closed set instead of inventing “Food & Bev”, so the human gets a correct default rather than a dropdown. The default on currency means nobody is ever asked. The descriptions on merchant and amount exist because a bare { "type": "string" } tells the model the shape and nothing about the meaning, and meaning is what it needs to decide what goes in there.

The subtraction exercise

Do this on paper before you open a design tool. It takes ten minutes and it is the highest-yield thing in this chapter. List every field your form has, one line each. Next to each, write where the value could come from: the conversation, a previous tool result, the user’s identity, a sensible default, or nowhere. Delete every row that is not “nowhere”, because those are schema properties now rather than form fields. Look at what is left; that is your widget. Then ask whether what is left is worth a render at all, using Chapter 1’s three questions.

Run on the gallery’s expense form, the exercise goes from nine rows to one, and step five very nearly deletes the widget. What saves it is that the user wants to see the amount before it is filed, which is a genuine case of needing to be seen rather than read, and which is why the fixed version leads with the number in the largest type on the card.

Prefill, and then show your work

Prefilling is half the job. The other half is making the prefill visible and correctable, because prefill without visibility is a confident guess that nobody audited.

The pattern that works has three parts. Show what you assumed, not in a tooltip but on screen, in the layout, as facts: the gallery’s confirmation puts merchant, date, employee, and cost centre in a small definition list, four things the user did not type into this widget and can check with one pass of the eye. Say where it came from, in one line at the bottom, because Employee, cost centre, amount, and date came from the receipt you sent is the single highest-value sentence in most widgets and it costs nothing. It converts a mysterious prefilled form into a summary the user can verify, and it converts a wrong prefill from a silent error into an obvious one. And make correction cheap and quiet: not a modal, not an edit mode, but a disclosure labelled with what is inside it, Change merchant, date, or category, closed by default and losing nothing when it stays closed.

That is progressive disclosure done honestly, which means fewer controls showing and everything reachable. The dishonest version hides things behind a gear icon labelled nothing and then congratulates itself on a clean interface.

When the prefill is wrong

Prefilling raises the cost of being wrong, and pretending otherwise is how this law turns into a bug report. The model inferred CC-ENG-7 from “my usual cost centre”. Suppose the user changed teams last month. The old widget asked and got the right answer; the new widget assumed and got the wrong one, silently, in a field the user was not looking at because they were looking at the amount.

That is a real regression and it deserves a real defence, which is the three parts above doing a second job. Showing the assumption at the same visual weight as the thing being confirmed is what makes the wrong value catchable: not in grey nine-point type at the bottom, but in the list of facts the user reads before pressing the button. Saying where it came from is what makes scepticism possible at all, because a value that was typed, one that was inferred, one that was looked up, and one that was defaulted deserve four different amounts of trust, and without a source line the user cannot tell which they are looking at. And a correction that is one click away and labelled with its contents is what makes fixing it cheaper than complaining about it.

The one thing that does not work is a confidence indicator. Nobody has ever usefully acted on “we are 80% sure this is your cost centre”. Show the value, show the source, make it editable, and let the human do the thing humans are good at. There is one case where asking still beats assuming even with all three defences in place: when the wrong answer is expensive and quiet. Filing to the wrong cost centre is discovered at month end by somebody who is annoyed. If your field is like that, ask, and spend the extra turn.

The default that is not a question

A default is an answer you supply, and a good default is an answer that is right often enough that questioning it is the exception. Declared in the schema it costs the model nothing and the user nothing:

currency:     { type: "string", default: "USD" },
cabin:        { type: "string", enum: ["economy", "business"], default: "economy" },
horizonYears: { type: "integer", minimum: 1, maximum: 10, default: 5 },

Three things a default has to do to be worth having. It has to be right most of the time, because a default that is right half the time is not a default, it is a coin flip with a confident face. It has to be visible, so the user can see what was assumed without opening anything, which is usually a job for the orientation line in Chapter 8. And it has to be cheap to change, in one control or one sentence to the assistant. The horizon slider in Chapter 1 exists because five years was a default worth questioning and questioning it in prose costs a turn. A default that fails any of those three is a question you decided not to ask and should have.

Every click is a tool call

Here is the part that is structurally different from the web, and it is why this is a law rather than a preference.

On a web page a click is free. It is a DOM event. Nobody approves it, nobody logs it, nobody sees a permission dialog. In this medium a click that does anything is a tools/call that travels from your sandboxed iframe to the host, through whatever consent policy the user has configured, out to the server, and back. Hosts may prompt. Depending on how the user set things up and how destructive the tool looks, hosts may prompt every time.

So every interactive control you add is a potential permission dialog you have added, and permission dialogs have a well-documented failure mode: after the fourth one, people stop reading them. That is not a hypothesis. It is the entire history of mobile permission prompts, and it is how consent fatigue turns a security feature into a rubber stamp. Which gives you a design rule with an unusually clear justification:

Every control you add spends a little of the user’s willingness to read the next consent prompt, including the ones that matter.

Four fields the model could have filled are not four small annoyances. They are four opportunities to teach somebody that clicking through is fine.

Teardown: nine fields becomes one confirmation

The task: the user sends a receipt and says “file it against my usual cost centre.”

Count what is being re-asked. Employee ID, which the system knows because it knows who is talking. Cost centre, which the user just referred to and which a lookup resolved two turns ago. Merchant, date, amount, and currency, all four of which are in the receipt and all four of which were in the sentence. That leaves category, which the model can infer given an enum, and justification, which is genuinely optional and genuinely unknown. Nine fields, of which two carry information the system did not already have. The other seven are a transcription exercise with a submit button.

There is a second failure here, quieter and worse. Look at what the model sees after this renders: nothing. The tool returned “Expense form opened.” The user now fills in nine fields and the model watches none of it, so when the user says “did that go through?” three turns later, nobody in the conversation knows. Law 2 and Law 3 fail together, as they usually do, because the same instinct produces both.

The amount is the headline, because that is the thing a person checks. The four known facts sit underneath as a list, verifiable in one pass. One field is open, and it is the one field nobody could have filled in for you. The disclosure holds the corrections, and the origin line says where the prefill came from. One question instead of nine, achieved by removing neither capability nor information, but by using what was already said.

When you genuinely need to ask

Sometimes you do need input, and the law does not forbid it. It forbids asking for what you already have. Three cases where asking is right: the information does not exist yet, as with a justification or a preference or a judgement call that nobody has expressed; the stakes justify confirmation, because “yes, delete the production database” is worth asking even when the intent is obvious, since the cost of being wrong is unbounded; and the user is exploring, dragging a slider that re-ranks or a filter that narrows, in which case nothing is being re-asked because the user is generating new information by playing with it. That third case is what earned the slider in Chapter 1.

The test that separates those from the violations is one question: if the user answered this already, would my widget notice? If the answer is no, you are not asking. You are interrogating.

Before you build a form at all, know that core MCP can ask a structured question for you with no widget involved. Chapter 9 opens on that option, because it wins more often than app developers like to admit.

What to remember

The conversation is a database and you have read access. Put fields in your schema so the model can fill them, because a field the model can fill is a field the user never sees. Show what you assumed, say where it came from, and put the correction one click away and closed by default. Every control you add is a consent prompt you might have added, and consent prompts are a shared resource you are spending on somebody else’s behalf.
