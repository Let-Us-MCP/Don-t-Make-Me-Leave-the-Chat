Norman split knowledge into two kinds. Knowledge in the world is information you
can see: the labels on the buttons, the shape of the plug, the position of the
dial. Knowledge in the head is what you have to remember: the command, the
password, which of the four identical switches is the one for the porch.

Interfaces that put knowledge in the world are easy. Interfaces that demand
knowledge in the head are the ones people write angry reviews about.

This medium has both, and the split falls in an unfamiliar place. Knowledge in
the world is what is on screen in your widget. Knowledge in the head is what is
in the model's context. And the second one is durable while the first one is
not, which inverts every instinct you have from building web applications.

## Two places to keep a fact

**In the widget.** Fast, private, and free. Slider positions, which disclosure is
open, scroll position, the half-typed text in a field. This state lives in the
frame and dies with it.

**In the context.** Slower, shared, costly, and durable. Anything the model needs
to answer a follow-up question. Anything that should survive the conversation
moving on. Anything a person would have said out loud.

The rule of thumb from Chapter 2 is the practical version: if a person would say
it, write it back; if it is a mouse position, do not.

Here is the sorting test, applied to a widget:

| Fact | Where |
|---|---|
| Which tab is open | Widget |
| Which flight the user picked | Context |
| Scroll position in the table | Widget |
| That the user changed the horizon to four years | Context |
| Whether the "advanced" disclosure is expanded | Widget |
| That the expense was submitted, and its ID | Context |
| The colour of the highlight | Widget |
| That the rollout reached 50% at 09:26 | Context |

The pattern: **decisions and outcomes go to the context; presentation stays in
the widget.**

## The problem that is genuinely new

Now the part with no web analogue.

Between your render and the user's next glance at it, the model can act.

It can call your tool again with different arguments. It can call a different
tool that changes the same underlying thing. It can do three of those in a row
because the user asked it to. And your widget knows about none of it, because
your widget is a static document in a sandboxed frame that was handed one result
and then left alone.

![Confidence stays flat. Truth does not.](figures/xkcd-staleness.png)

On the web this happens too, and we handle it with polling, sockets, and
optimistic updates. What is different here is the *source* of the change. It is
not another user in another city. It is the same user, in this conversation,
thirty seconds ago, using words instead of your buttons.

Which makes the staleness feel like a lie rather than a race condition. The user
literally just told the assistant to do the thing. Your widget, three inches
away on the same screen, is still displaying the world as it was before they
said it.

## Three honest responses

You have three options, and the wrong one is to pretend the problem does not
exist.

**Timestamp everything.** The cheapest fix, and it closes most of the gap. Say
when you read the world. `As of 09:41 UTC.` One line. It converts an assertion
about the present into a report about a moment, which is what it actually was.

**Decay visibly.** After some interval, say that you might be behind and offer to
check. The gallery's tracker does this after twenty seconds:

```javascript
setInterval(function () {
  if (lastFetch && Date.now() - lastFetch > STALE_AFTER_MS) {
    document.getElementById("stale").classList.add("show");
  }
}, 2000);
```

A badge saying *may be out of date* and a *Check now* button. Eleven lines. It
is more honest than polling, because polling makes the widget look live without
making it live, and a widget that looks live is a widget that gets believed.

**Refresh on demand, and let the model trigger it.** The best version, when the
data supports it. The refresh path is the same tool call the model would make,
which means the tool has to be safe to call repeatedly. Design for that: the
gallery's `deploy_status` description says so out loud, *Safe to call again when
the user asks whether anything changed*, because that sentence is a door handle
for the second user.

What you should not do is fake liveness. An auto-refresh indicator on a widget
that fetched once is worse than no indicator, because it converts an
inconsistency the user might have caught into one they will not.

## Re-render from context

"Show me that dashboard again" should work.

It is a completely reasonable thing to say four turns later, and in this medium
it is not a navigation request. There is no back button and no URL. It is a
request for the model to call the tool again.

For that to produce the *same* dashboard rather than a generic one, two things
have to be true.

**The tool must accept the parameters that made it specific.** If the user's
dashboard was scoped to a release, a date range, or an account, those have to be
arguments, not internal state. A tool with an empty input schema cannot be
re-summoned specifically. This is the same lesson as Chapter 4, arriving from a
different direction: your input schema is the vocabulary the model has for
talking about your app.

**The model must know what those parameters were.** Which means they were
written back, in `content` at render time and in `ui/set-context` whenever the
human changed them.

Put those together and you get a small design contract:

> Anything a user might want to return to must be expressible as arguments to
> your tool, and the model must have been told the values.

The gallery's rate comparison satisfies this: `horizonYears` is an argument, and
every slider change writes back `{ horizonYears: 4, cheapest: "...", totalCost: ... }`.
Ask for it again at any point and the same comparison comes back, at the horizon
you left it on.

The before version does not satisfy it. Its schema is empty, so "show me that
again" produces the default view and the user does the work twice.

## Teardown: two deploy trackers

The task: "ship 2026.8.14 and keep an eye on it."

![Figure 7-1. `deploy_tracker`. Rendered once, then frozen, and confident about it.](figures/fig-7-1.png)

This one is a nice piece of work. Clean step list, status dots, a start time.

It has one fetch in its entire lifetime. Everything after that is a picture of a
moment that has passed. The canary finished two minutes ago; this widget will
say `running` until the conversation ends.

Look at the transcript underneath. The user asks "did the canary finish?" and
now the model has to answer. It has one piece of information, from the original
tool result, and that information says `running`. So the model says the canary
is still running, in text, next to a widget that also says `running`, and the
user has two independent-looking confirmations of something that is false.

That is the real cost. Not that the widget is stale. That the widget's staleness
became the model's answer, so the error got laundered into confidence.

Notice also the header: *Started 09:22 UTC*. A start time and no read time. The
one timestamp it shows is the one that cannot go stale, and the one it needs is
missing.

![Figure 7-2. `deploy_status`. Same data, plus a read time, a refresh, and a write-back.](figures/fig-7-2.png)

Four changes, none of them large.

*Read from the deploy API at 09:26 UTC* at the bottom. The phase as a pill, so
the verdict is at level one. A `may be out of date` badge that appears on a
timer, with a `Check now` button next to it. And `setContext` on every paint, so
the model has the phase, the summary, and the read time without another render.

Now "did the canary finish?" gets answered from context that includes its own
timestamp, and if the model is unsure it can call the tool again, because the
tool said it was safe to.

## Optimistic updates, and when to lie

One nuance, because the advice above can be read as "never show anything you
have not confirmed", which would make every widget feel slow.

Optimistic updates are fine. Show the state the user just asked for, immediately,
before the round trip completes. That is not staleness; it is responsiveness, and
users read the delay as breakage.

The rule is that the optimism has to be *reversible and visible*. If the call
fails, say so, in place, and put the old value back. And do not write an
optimistic state to the model's context, because the model cannot see your
rollback. Write back on confirmation only.

Optimistic in the world, confirmed in the head. That is the split this chapter
is about, doing useful work.

## What to remember

Presentation lives in the widget and dies with it. Decisions and outcomes go to
the context and survive. The model can act between your renders, so a widget
that asserts the present tense without a timestamp is claiming more than it
knows. Timestamp, decay visibly, refresh on demand, and make your tool safe to
call again so the model can do it for you.
