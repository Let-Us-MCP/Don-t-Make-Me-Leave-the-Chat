This chapter exists so that no other chapter has to stop and explain the wire.

It is deliberately short and deliberately incomplete. *High-Performance MCP
Applications* covers the protocol down to the bytes. *Patterns of MCP App
Architecture* covers what happens when you have forty of these things in
production. What follows is the minimum a designer needs to make good
judgements, which turns out to be about six facts.

## Six facts

**1. UI is a resource, declared in advance.**

Your server publishes an HTML document at a `ui://` URI, with the MIME type
`text/html;profile=mcp-app`. It exists before any tool is called. That is what
makes prefetching possible, and prefetching is what makes the first render fast.

**2. A tool points at it.**

A tool becomes an app by carrying `_meta.ui.resourceUri`. That is the whole
attachment mechanism.

```javascript
registerAppTool(server, "compare_rates", {
  title: "Compare loan rates",
  description: "Show a comparison of the loan offers under discussion...",
  inputSchema: { /* ... */ },
  _meta: { ui: { resourceUri: "ui://rate-compare/after" } },
}, handler);
```

Tools without that field are ordinary tools that return text. Both kinds can
live on the same server, and a well-designed server usually has both.

**3. It runs in a sandboxed iframe.**

The host puts your document in an iframe with a restrictive sandbox. Your app
cannot read the host's DOM, cookies, or storage. It cannot navigate the parent.
The host also applies a Content Security Policy built from what you declared in
`_meta.ui.csp`, and the default is deny.

**4. Everything crosses by `postMessage`.**

The app talks to the host over `window.postMessage`, in JSON-RPC. Some methods
are shared with core MCP (`tools/call`). Most are new and prefixed `ui/`
(`ui/initialize`, `ui/set-context`, `ui/size-changed`, `ui/open-link`). Every
message is loggable, which is what makes the medium auditable.

**5. Results come in two shapes.**

A tool result carries `content` (for the model) and `structuredContent` (for
your app). Chapter 2 is about the consequences of that.

**6. It is an extension, and it negotiates.**

MCP Apps is `io.modelcontextprotocol/ui`, an optional extension. Client and
server both declare it, and if either side does not, you get core behaviour:
the tool runs and the text comes back. Which means your `content` string is not
a nicety. In several hosts it is the whole product.

### Registering both halves

Two registrations, and they are the entire server-side surface of the extension.

```javascript
// The tool. `_meta.ui.resourceUri` is what makes it an app.
registerAppTool(server, "compare_rates", {
  title: "Compare loan rates",
  description: "Show a comparison of the loan offers under discussion, ...",
  inputSchema: { type: "object", properties: { horizonYears: { ... } } },
  _meta: { ui: { resourceUri: "ui://rate-compare/after" } },
}, handler);

// The resource. One self-contained HTML document.
registerAppResource(server, "ui://rate-compare/after", "ui://rate-compare/after",
  { mimeType: "text/html;profile=mcp-app" },
  async () => ({ contents: [{
    uri: "ui://rate-compare/after",
    mimeType: "text/html;profile=mcp-app",
    text: await readFile("dist/rate-compare.html", "utf8"),
  }] }));
```

Two things about that HTML are worth stating because they trip people.

**It is one document.** Styles inline, scripts inline, images as data URIs. Not
because bundling is fashionable, but because the CSP the host builds from your
declaration is deny by default, and an external stylesheet is an external
request. The gallery resolves shared partials at serve time; a real project
usually reaches for a single-file bundler.

**It has no server of its own.** There is no origin to fetch from, no cookies to
send, no session. Everything it knows arrives over `postMessage`. If your mental
model of the app still has an API call in it, that call is a `tools/call`
through the host now.

## The lifecycle in one page

![One render, from predeclaration to teardown.](figures/diag-lifecycle.png)

**Predeclare.** The server lists the `ui://` resource. Nothing has happened yet.

**Prefetch.** The host may fetch the template ahead of time, on connect or on
first sight of the tool. Your HTML is now sitting in the host, ready.

**Render.** The model calls the tool. The host renders the template immediately,
before the tool result exists. Your app is on screen with no data.

**Data delivery.** The arguments arrive first, then the result. In the gallery's
bridge these are `ontoolinput` and `ontoolresult`. The gap between them is real
and sometimes long, which is why Chapter 3 treats the skeleton as a designed
screen.

**Interact.** The human does something. Your app calls `tools/call` for actions
and `ui/set-context` for state the model should know about. The host mediates
both, applies consent policy, and logs everything.

**Teardown.** The conversation moves on. The frame goes away. Anything you did
not write back is gone.

That last sentence is the one to remember. The frame is transient. The
transcript is durable. Chapter 7 is entirely about the consequences.

## The four messages you will actually write

Six facts is enough to reason with. Four messages is enough to build with. Here
they are, in the shapes the gallery's bridge uses. The ext-apps specification is
normative and has more of them; these are the ones that carry the arguments in
this book.

**Handshake.** Your app announces itself and finds out where it landed.

```javascript
// app -> host
{ "jsonrpc": "2.0", "id": 1, "method": "ui/initialize",
  "params": { "appInfo": { "name": "Rate comparison", "version": "1.0.0" },
              "capabilities": { "toolCalls": {}, "context": {} } } }

// host -> app
{ "jsonrpc": "2.0", "id": 1,
  "result": { "hostInfo": { "name": "claude", "version": "..." },
              "capabilities": { "toolCalls": {}, "context": {}, "openLink": {} },
              "theme": { "mode": "dark", "cssVariables": { "--ink": "#E7EAEE" } } } }
```

Read the `capabilities` that come back. They are not decoration. A host that
omits `toolCalls` will refuse every action your buttons trigger, and finding
that out at click time means the user found out first. Chapter 12 is about
designing for the answer.

**Data in.** The host pushes twice, and the gap between them is real.

```javascript
// host -> app, as soon as the model has decided
{ "jsonrpc": "2.0", "method": "ui/tool-input",
  "params": { "arguments": { "horizonYears": 5 } } }

// host -> app, when the server answers
{ "jsonrpc": "2.0", "method": "ui/tool-result",
  "params": { "content": [ { "type": "text", "text": "..." } ],
              "structuredContent": { "horizonYears": 5, "offers": [ ... ] } } }
```

Two callbacks, two states, both of them screens somebody sees.

**Action out.** Your button becomes a tool call, and it goes through the host.

```javascript
// app -> host, forwarded to the server if policy allows
{ "jsonrpc": "2.0", "id": 2, "method": "tools/call",
  "params": { "name": "hold_flight", "arguments": { "number": "UA 512" } } }
```

Note whose name is on that message. The host is the one that calls the server.
Your app asked. That indirection is where consent, logging, and refusal live,
and it is the reason Chapter 4 treats every control as a tax.

**State back.** The one most apps forget.

```javascript
// app -> host, written into the conversation
{ "jsonrpc": "2.0", "id": 3, "method": "ui/set-context",
  "params": { "content": [ { "type": "text",
                "text": "Comparing over 4 years: Northbank is cheapest at $34,769." } ],
              "structuredContent": { "horizonYears": 4, "cheapest": "Northbank" } } }
```

Two fields again, for the same two users, for the same reason.

There is a fifth you should send and will not think about: `ui/size-changed`,
which tells the host how tall you are. Send it after every render and after
every disclosure toggle. A widget that reports its height once and then grows is
the thing Chapter 10 calls out as the most annoying move available to an
interface.

## Negotiation, in two lines

The extension is opt-in on both sides. The client declares what it can render:

```json
"_meta": {
  "io.modelcontextprotocol/clientCapabilities": {
    "extensions": { "io.modelcontextprotocol/ui": {
      "mimeTypes": ["text/html;profile=mcp-app"] } }
  }
}
```

And the server declares that it has apps to offer:

```json
"capabilities": {
  "tools": {},
  "extensions": { "io.modelcontextprotocol/ui": {} }
}
```

If either side is silent, the tools still work. The model calls them, the server
answers, the text comes back, and nothing renders. That is the design of the
extensions framework rather than a degradation of it, and it is why the
specification tells servers to return meaningful text for clients that do not
support the UI.

## What the sandbox promises the user

The sandbox is not a limitation imposed on you. It is a promise made to the user
on your behalf, and it is the reason a stranger's HTML is allowed to render
inside a conversation that also contains their tax return.

Specifically, it promises:

- Your app cannot read the transcript. Only what the host hands you.
- Your app cannot reach the user's session, cookies, or local storage.
- Your app cannot navigate the page or open windows behind the user's back.
- Your app cannot call anywhere you did not declare, and the host enforces it.
- Every action your app requests passes through the host, where it can be
  refused, logged, or shown to the user first.

Two design consequences follow, and both are load-bearing for later chapters.

**Do not fight it.** Every trick for widening the sandbox is a trick that will
be closed, and the closing will be a production incident. If your design needs
`allow-same-origin` to work, your design needs changing.

**Declare less than you can.** An app that declares no external origins is
making a statement the host can verify and the user can be shown. Chapter 10
argues that this is a design decision with a real effect on trust, not a
security checkbox to be maximised.

## `content` versus `structuredContent`

Same fact, two renderings, one source. Chapter 2 made the design argument; here
is the mechanical shape.

```javascript
run({ horizonYears = 5 }) {
  const offers = priceOffers();          // computed once
  const ranked = rankOffers(horizonYears);
  return {
    content: [{
      type: "text",
      text: `Comparing ${offers.length} offers over ${horizonYears} years. ` +
            `${ranked[0].lender} is cheapest at ${money(ranked[0].total)}. ` +
            `The user can change the horizon in the app.`,
    }],
    structuredContent: { horizonYears, offers },
  };
}
```

The `content` string is written for a reader. It says what happened, what the
answer is, and what the human can do next. A model that never renders your app
can still answer questions from that sentence, which is exactly what happens in
hosts that do not support the extension.

The `structuredContent` object is written for your app, and it is the *complete*
data, including the eight horizons the user has not selected. That is deliberate:
the slider then needs no round trip, and no arithmetic happens twice.

Three rules that prevent most of the pain here:

- **Compute once.** Derive both from the same call.
- **Write `content` for a reader, not a log.** "Loan analytics suite opened." is
  a log line. It tells the model nothing it can use.
- **Put in `structuredContent` what the app needs, plus what the model will be
  asked about.** Figure 5-2 drops seven columns from the pixels and keeps them
  in the data, so "which one is the widebody" is answerable in text.

## Three things that surprise people

**The template is cached and the data is not.** That split is the point of
predeclaration. Your HTML is fetched once and reused across renders; your data
arrives fresh each time. Which means anything you bake into the HTML is
effectively permanent for the session, and anything that changes belongs in
`structuredContent`. A widget that hard-codes today's date into its markup will
be wrong tomorrow and nobody will know why.

**Your app can be rendered more than once in one conversation.** Two calls, two
frames, both alive, both on screen, both holding their own state. They do not
know about each other. If that matters for your archetype, the transcript is the
coordination mechanism: write state back, and let the model reconcile.

**The height is a request.** You send `ui/size-changed`; the host decides. It may
grant it, cap it, or ignore it. Design so that a smaller allocation degrades to
scrolling inside your own container rather than to clipped content, and never
position anything important below a fold you do not control.

To keep the promise made at the top of this chapter, here is what this book will

What this book does own is the question of whether to render at all, and what to
put in the render. Everything from here on is that.

## Reading the specification after this

At some point you will need the normative document, and it helps to know what
you are looking for.

Go to it for **field names and their exact shapes**, especially under `_meta.ui`:
the CSP declaration, the permissions list, size hints, and whatever has been
added since. Books are the wrong medium for that and this one does not try.

Go to it for **the full method list**. This chapter covered four messages. There
are more, and some of them matter for archetypes this book treats lightly.

Go to it for **the security model in full**. The threat model behind the sandbox
is written down, and Chapter 10 argues from it rather than restating it.

Do not go to it for **whether to render**. The specification is deliberately
silent on judgment, which is the entire reason this book exists.

One practical note on reading it: the extension moves faster than the core
protocol, by design, since extensions evolve independently. Pin your reading to
a dated revision the way this book does, and re-check the fields when you
upgrade.

## What to remember

UI is a predeclared `ui://` resource, attached to a tool by
`_meta.ui.resourceUri`, rendered in a sandboxed iframe, spoken to over
`postMessage` in JSON-RPC. The template renders before the data arrives. The
frame is transient and the transcript is durable. The result carries text for
the model and data for the app, and they should come from one computation. And
the whole thing is an optional extension, so the text path is not a fallback you
tolerate. It is a product you ship.
