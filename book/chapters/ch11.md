Krug's testing chapter is the most useful thing he wrote, and the argument was
about economics rather than method. Elaborate usability testing is expensive, so
it happens once, late, when nothing can be changed. Cheap testing is worth more
than good testing, because cheap testing happens.

His numbers: three to five users, one morning a month, watched by whoever can be
dragged into the room. That finds most of what an expensive study finds, at
about one percent of the cost, early enough to act on.

![Krug's curve, unchanged. The audience doubled; the curve did not.](figures/xkcd-testing.png)

All of that transfers unchanged. Then this medium doubles the audience.

## The human half, unchanged

Five people. Three tasks. One afternoon. Somebody watching.

**Recruit loosely.** Krug's finding that recruiting the "wrong" users still
finds most problems holds here. You are looking for interface failures, not
domain expertise.

**Give tasks, not instructions.** "Find out whether we can get out of the
Northwind contract early" is a task. "Click the find clause button" is a
rehearsal.

**Watch, do not help.** The urge to explain is overwhelming and it destroys the
data. Every explanation you give in the room is one you cannot give in
production.

**Ask them to think aloud.** Especially in this medium, because half the
interaction is what they *typed*, and you need to hear what they expected the
assistant to do.

**Stop after each session and fix something.** Five sessions and one fix at the
end is worse than five sessions with four fixes between them.

Three things to watch for that are specific to chat:

- **What did they type?** If nobody phrases the request the way your tool
  description expects, your app will not get invoked in the wild. This is a
  finding about your description, not about your user.
- **Did they notice the widget?** In a scrolling transcript, on a phone, a
  render can be missed entirely. If they scrolled past it and typed a follow-up
  question instead, that is the answer to Chapter 1's first question.
- **Did they touch the controls?** A control nobody touches in five sessions is
  a control you can delete. This is the cheapest deletion criterion in the book.

### What five sessions actually look like

The advice above is easy to agree with and easy to not do, so here is the shape
of an afternoon that has actually happened, compressed.

**Session one.** The user types "compare these loans". The tool does not fire;
the model answers in prose from the numbers already in the conversation. That is
finding number one, and it is not a bug in the widget. It is the description not
saying that this tool is for when the answer should be adjustable.

Fix between sessions: add the trigger sentence.

**Session two.** The widget fires. The user reads the headline, says "so the
credit union", and moves on without touching the slider. Finding two: the slider
may not be earning its place. Not yet actionable, because one person is not
data.

**Session three.** Same, but this user drags the slider immediately and says
"oh, that changes it". Finding two is now interesting rather than damning, and
the difference between these two users is worth understanding rather than
averaging.

**Session four.** The user asks a follow-up: "what was the monthly on the
Northbank one?" The model answers correctly, because the monthly is in
`structuredContent`. That is not a finding; it is a control passing, and it is
worth noticing when something works.

**Session five.** The user scrolls back to the render twenty minutes later and
reads the old numbers as current. Finding three, and it is the Chapter 7
problem, found in the wild in about four seconds.

Three findings, two fixes, one open question, one afternoon. That is a normal
yield, and it is why the method survives contact with a schedule.

## The new half: the model as a user

Now the part with no precedent, and the part you can run every commit.

Your other user can be tested automatically, at scale, without recruiting
anybody, because it is software. And it needs testing more than the human does,
because you never watch it use your app. You watch the transcript afterwards and
infer.

There are three questions, and they map onto the three ways an app fails its
second user.

**1. Invocation.** Given a prompt that should use your app, does the model use
it? Given one that should not, does it stay away?

Under-invocation is the common failure and it is nearly always the description.
The tool is fine, the app is beautiful, and the model never reaches for it,
because the description says what the tool *is* instead of when to use it.

Over-invocation is rarer and more annoying. A tool described too broadly gets
called for everything, and now every conversation has a widget in it.

**2. Argument quality.** When the model does call, does it pass what it knows?

This is Law 3 measured. If the conversation contained the date and the model
called your tool without it, you have found either a missing schema property or
a property whose description does not say what goes in it.

**3. Readback.** After the render, can the model answer questions about what
happened?

Ask a follow-up that depends on the widget's state. If the answer is wrong or
hedged, your write-back is missing or too thin. This is the check that catches
Figure 2-1, and it catches it in about four seconds.

## The harness that runs without a model

Before you spend anything on model-in-the-loop runs, there is a tier of checks
that need no model at all, run in under a second, and catch most of what goes
wrong. The gallery ships them in `gallery/evals/checks.js`.

Each one is a question the model would ask about your tool, expressed as a
grep:

- **Does the description say when to use this?** A regex for *use when*, *when
  the user*, *call this when*. Crude, and it works, because a description with
  no trigger clause is a description that never says when.
- **Does the tool have more than one address?** An empty `properties` object
  means the model cannot re-summon a specific view, so the app has to ask the
  user for everything. Chapters 4, 7, and 8 all end up here.
- **Is the text answer an answer?** If `content` is under nine words, it is
  almost certainly a log line. "Loan analytics suite opened." tells the model
  nothing it can use.
- **Does an interactive app ever write back?** If the HTML binds a click handler
  and never calls `setContext`, the second user is locked out.
- **Does anything that changes the world name a way back?** Chapter 9's
  requirement, checked mechanically.

None of that is clever. All of it has caught something.

## A worked session

Here is what happened the first time those checks ran against this book's own
gallery. The apps had just been written, by somebody who had just finished
writing the chapters telling you not to make these mistakes.

```
21 tools checked, 20 error(s), 15 warning(s)
```

Twenty errors. Some of the findings, verbatim:

```
FAIL  service_status  [empty-schema] no input properties, so the model cannot
                      re-summon a specific view and the app must ask the user
                      for everything
FAIL  submit_expense  [log-line] content reads as a log line rather than an
                      answer: "Expense EXP-91909 submitted. Void it with
                      void_expense."
FAIL  pick_flight     [no-trigger] description never says when to reach for
                      this tool
warn  submit_expense  [bare-property] property "amount" has no description,
                      enum, or default
```

Three of those are worth dwelling on.

`service_status` had an empty input schema. It is the chapter-3 exhibit of doing
a dashboard right, and it could not be scoped to a service, which means "just
show me checkout" produced the whole platform. Chapter 7's re-render contract
failed on the book's own example.

`submit_expense` returned a sentence that reads fine to a person and tells the
model nothing about what was filed. The amount, the merchant, and the date were
all in `structuredContent` and none of them were in the text, so a host without
the extension got a receipt number and no receipt.

`pick_flight` had a good description that never said when to use it. It said
what not to do (*do not call this before origin, destination, and date are
known*) without ever saying what to do.

Fixing all twenty took about forty minutes and touched only descriptions,
schemas, and `content` strings. Not one pixel changed. That is the shape of this
work: the second user's entire interface is text, so its bugs are text bugs, and
text bugs are cheap.

## The model-in-the-loop tier

The checks above are a filter. They tell you a description has no trigger
clause. They cannot tell you whether the trigger clause works.

For that you need a model, a prompt suite, and a host. The cheap version is a
headless run against a host you already have. From the repository root:

```bash
claude -p "Using only the gallery MCP server, answer in exactly two lines: \
  which lender is cheapest over five years and the total, and whether that \
  changes at three years." \
  --allowedTools "mcp__gallery__compare_rates_text"
```

```
Cedar Credit Union is cheapest over five years at $34,835 total (vs. Harbor
Direct $34,965 and Northbank $35,000).
Yes, it flips at three years: Northbank wins at $34,130 ... Cedar's $1,400 in
fees only pays off over a longer horizon.
```

That is an invocation check, an argument check, and a readback check in one
command, and it costs about ten cents.

Build a suite of ten prompts per app. Five that should invoke it, phrased the
way five different people would phrase it. Three that should not, including at
least one near miss. Two that check readback after a render. Run them nightly,
or on every change to a description, which is where the regressions come from.

Here is a real suite, for the gallery's flight picker, written the way five
different people would ask:

```
INVOKE   "book me a flight to New York Thursday morning"
INVOKE   "what are my options for getting to JFK on the 20th"
INVOKE   "I need to be in New York by lunchtime Thursday"
INVOKE   "sort out the travel for the Thursday meeting, economy, just me"
INVOKE   "same as last time but Thursday"            (context in earlier turns)
SKIP     "how much do flights to New York usually cost"   (a question, not a booking)
SKIP     "cancel my Thursday flight"                       (a different tool)
SKIP     "what is the baggage allowance on United"         (answerable from context)
READBACK "which one did I pick?"                           (after a selection)
READBACK "what time does it land?"                         (needs structuredContent)
```

The third and fifth are the interesting ones. Neither mentions a flight, an
airport, or a date in the form your schema wants, and both are how people
actually talk. If your description only survives the first two phrasings, it
will get invoked in demos and not in use.

Two warnings from running this in anger.

**Model runs are not deterministic.** A single failure is noise. Run the suite
three times and look at rates. A prompt that invokes correctly two times out of
three is a description problem, not a flake.

**Record the prompts, not the outputs.** Outputs change with every model
release. What you are testing is whether your description survives the
paraphrase, and the prompt suite is the durable artefact.

## What to fix first

Krug's triage, adapted. In order:

**1. Things that make the model not call you.** Nothing else matters if the app
never renders. This is almost always the description, and it is almost always a
missing trigger clause.

**2. Things that make the model wrong afterwards.** A widget that leaves the
model with a stale or absent picture produces confident wrong answers, and
confident wrong answers cost more trust than a missing feature.

**3. Things that make the human ask a question they already answered.** Every
re-ask found in a session is a schema property you did not declare.

**4. Everything else.**

Resist the urge to fix the visual problems first. They are the ones you can see,
which is why they get fixed, and they are usually the ones that matter least.

## Wiring it into CI

The static checks belong on every commit, because the things they catch are
edits somebody makes at five o'clock.

```yaml
- name: Every app parses and connects
  run: node tools/check_apps.mjs

- name: Model-as-user checks
  run: node gallery/evals/run.js --all
```

Two jobs, no dependencies, about twenty seconds. What they buy is that the class
of bug which is invisible in review stops reaching main.

The invisible one is worth naming. A mismatched quote in one of the gallery's
apps meant its script never ran, so it never called `ui/initialize`, so the host
waited forever and the widget rendered as an empty box. No error appeared
anywhere: not in the server log, not in the host, not in a test. A syntax error
inside a sandboxed iframe is silence. `check_apps.mjs` exists because of that
afternoon, and it now parses every app's script before anything else runs.

The model-in-the-loop suite does not belong on every commit. It costs money and
it is non-deterministic, so run it nightly, and on any change to a tool
description, which is where invocation regressions come from and where nobody
thinks to look.

## What to remember

Five humans, three tasks, one afternoon, and fix something after each session.
Then test the other user, which is cheaper because it never gets tired: does the
model invoke you, does it pass what it knows, and can it answer afterwards. Most
of that runs as static checks in under a second. The rest costs ten cents a run
against a host you already have. And when the checks fail on your own examples,
which they will, notice how many of the fixes are strings.
